# ADR-0002: 不引入 ViewModel 基类，三态样板交给 `runAsync` 函数

> ## ⚠️ 适用范围：仅对 master（signals 栈）成立
>
> 本 ADR 的载体（`runAsync` 函数、`asyncSignal`、`@injectable` 的 `factory` 生命周期、
> signal 的 `disposed` 语义）都随 signals 栈一起留在 master。`preset/ai-starter`（Riverpod）
> 分支上：
>
> - **结论仍然成立**：同样不引入任何 Notifier 基类（异步三态由 `AsyncValue` 承载，
>   项目侧没有可收敛的样板）。
> - **推导过程不适用**：`runAsync` / `SignalsWriteAfterDisposeError` / `Computed.dispose()`
>   不退订 `sources` 那条边界整节作废（`ref.watch` 的依赖由 provider 生命周期管理）。
>   保留下来的是原则「主动订阅就要主动退订」→ `ref.onDispose`。
>
> 分支上的对应内容见 `.trellis/spec/frontend/state-management.md` 的 Overview 与
> 「master 的 dispose 边界为什么整节作废」。**正文保持原文不动**。

## 上下文

ViewModel 里反复出现同一段三态样板：

```dart
_articles.value = AsyncState.loading();
final result = await repo.getArticles();
result.when(
  success: (d) => _articles.value = AsyncState.data(d),
  failure: (f) => _articles.value = AsyncState.error(f),
);
```

早期版本用一个抽象的 `BaseViewModel` 收敛这段重复：每个 ViewModel 继承它，由基类提供 loading/data/error 的流转，以及一个 `disposed` 守卫。

## 决策

**不引入任何 ViewModel 基类。** 三态收敛交给一个顶层函数 `runAsync`（`lib/core/base/run_async.dart`），ViewModel 继续是普通的 `@injectable` 类：

```dart
@injectable
class ArticleViewModel {
  final ArticleRepository _repo;

  ArticleViewModel(this._repo);

  final articles = asyncSignal<List<Article>>(AsyncState.loading());

  Future<Result<void, Failure>> loadArticles() =>
      runAsync(articles, () => _repo.getArticles());
}
```

## 理由

1. **真正共享的行为只有一个**。去掉各 ViewModel 的差异之后，`BaseViewModel` 里被复用的就只有 `runAsync` 这一步。为一种模式引入抽象类不划算。
2. **不干扰构造方式**。ViewModel 的依赖用构造器注入（见 [ADR-0001](./ADR-0001.md)），基类会额外引入继承层级与初始化顺序问题。
3. **不需要 dispose 守卫**。ViewModel 注册为 `factory`，每页一个实例、随页面被 GC 回收；页面销毁后没有监听者，此时再写一次 signal 只是无意义的赋值。基类里那个 `disposed` 守卫是在为一个不存在的问题付成本。
4. **函数比类好组合**。`runAsync` 可以在任意方法里直接调用，不必先成为某个基类的子类。

## 影响

- ViewModel 是普通类，signal 直接公开，不继承任何东西
- 新增 ViewModel 时直接调用 `runAsync`
- 需要把 `Result` 交给调用方做分支处理的方法，直接 `return runAsync(...)`（约定见 `.trellis/spec/frontend/state-management.md`）
- 没有基类可挂生命周期钩子：页面级资源由页面自己（`useEffect` / `useMemoized`）管理
- **不需要在页面销毁时 dispose ViewModel**：这是理由 3 的直接推论，但成立的前提是「VM 的信号只与自己的信号互相订阅」。前提被打破（VM 订阅了长生命周期的全局信号）时会真的泄漏——失效场景、源码依据与解法见 `.trellis/spec/frontend/state-management.md` 的「什么时候才需要 dispose」

## ADR 冲突

不涉及——与 ADR-0001 同向：两者都要求 ViewModel 保持「普通类 + 构造器注入」。
