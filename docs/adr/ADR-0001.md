# ADR-0001: ViewModel 使用构造器注入而非内部 Service Locator

**状态**：Accepted  
**日期**：2026-07-09  
**关联候选**：[architecture-review](../architecture-review.md) 候选 1（ViewModel 构造器注入）

---

## 上下文

ViewModel 层需要访问 `ArticleRepository` / `AuthRepository` 等依赖。注入方式有两种选择，且 `@injectable` 和 `injectable_generator` 都已就位。

## 决策

**ViewModel 的依赖通过构造参数注入，不在构造器内部调用 `getIt<T>()`。**

```dart
// ✅ 正确：构造器注入
@injectable
class ArticleViewModel {
  final ArticleRepository _repo;
  ArticleViewModel(this._repo);
  // ...
}

// ❌ 避免：内部 Service Locator
@injectable
class ArticleViewModel {
  final ArticleRepository _repo = getIt<ArticleRepository>();
  ArticleViewModel();
}
```

Widget 仍通过 `getIt<ViewModel>()` 获取 ViewModel——只消除 ViewModel 内部的 `getIt()` 调用。

## 理由

1. **依赖图可见**：构造器签名声明了所有依赖，不需要翻看构造器体去找隐式 `getIt()` 调用。
2. **测试不依赖全局状态**：测试只需 `ArticleViewModel(mockRepo)`，不需要在 `GetIt.I` 上注册/重置单例。
3. **Injectable 注册代码在编译期生成**：`getIt()` 的调用从运行时（ViewModel 构造）移到了注册时（`registerFactory` lambda），依赖错误提前暴露。
4. **IDE 重构友好**：构造参数变更时，所有注入点（包括注册代码）一起变。

## 影响

- 所有 ViewModel 的依赖都通过构造参数声明。
- Widget 层的 `getIt<ViewModel>()` 不受影响。
- 测试不必再操作全局 `GetIt.I` 来 mock **ViewModel 的依赖**——但页面自身仍从容器取 ViewModel，页面测试依然要初始化容器（见下）。
- `injectable_generator` 自动为构造参数生成 `gh<Repo>()` 调用。

## 已知代价：页面层仍是 Service Locator

本 ADR 只覆盖 `features/*/logic`（脚本对页面只加一条：检查可选注入点在不在，见下）。
页面（`features/*/page`、`lib/app/pages`）依旧通过 `getIt<ViewModel>()` 取 ViewModel。

代价落在**可测性**上：widget 测试必须先把全局容器装配好，页面才 pump 得起来，
于是 `test/support/app_test_harness.dart` 的 `setUpTestApp()` 成了页面测试的必需前置。

- 测试之间经由全局单例耦合——`GetIt.I.reset()` 漏了、或执行顺序变了就会互相污染。
- 没法只靠构造器把假 ViewModel 塞进页面。

### 为什么不把注入下沉到页面

页面若改成 `LoginPage({required AuthViewModel vm})`，就必须有人来提供它——而唯一能提供的
人是 `@RoutePage()` 生成的路由（`router.gr.dart` 里的 `const LoginPage()`）。这会把**路由与
DI 绑死**，依赖还得渗进 route args（破坏深链）。对脚手架而言不划算，故接受上面的代价。

### 缓解措施：可选注入点

从容器取 ViewModel 的页面**必须**开一个**可选**构造参数，默认回落到 `getIt`：

```dart
@RoutePage()
class LoginPage extends HookWidget {
  final AuthViewModel? viewModel;              // 只有测试会传
  const LoginPage({super.key, this.viewModel});

  @override
  Widget build(BuildContext context) {
    final vm = useMemoized(() => viewModel ?? getIt<AuthViewModel>());
    // ...
  }
}
```

- 路由侧 `const LoginPage()` 照旧（参数可选，生成代码无需改动）。
- 测试侧 `LoginPage(viewModel: fakeVm)`，`??` 短路，**完全不碰 GetIt**。
- 代价：页面里留下"两条路径"的分支；注入点的**存在**由脚本强制，**测试是否真的走注入路径**仍无人强制（那要求跨文件分析 `test/`，脚本只扫 `lib/`）。
- **已门禁**：`tool/check_boundaries.dart` 的规则 4 检查这三行是否齐全（`final T? viewModel;` + `this.viewModel` + `viewModel ?? getIt<T>()`），新页面漏给会直接拦提交。

当前采用此方式的页面：`login_page`、`article_list_page`、`article_detail_page`、
`storage_demo_page`——恰好就是 `lib/` 里全部 4 个从容器取 ViewModel 的页面；
示范测试见 `test/features/auth/page/login_page_test.dart`。

> 例外：`home_page` / `profile_page` 是直接 `getIt<AuthStorage>()` / `getIt<UserPreferences>()`
> （不是取 ViewModel），因此它们的测试仍需要 `setUpTestApp()`。
> 规则 4 只认 `*ViewModel`，这两页不在它的管辖内。

不涉及——新约定，无冲突。
