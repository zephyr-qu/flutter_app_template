# 注释规范

> 代码注释只留「一句提示 / 这个类是做什么的 / 一个示例」；为什么这么设计、踩过的坑、完整规则放 `.trellis/spec/`。
> 本文件管四件事：**代码注释写什么**、**spec 引用怎么写**、**spec 自身的语言与快照约定**、**spec 该怎么写**。

---

## 代码注释：三条

1. **一句提示** —— 说明这段代码在做什么，或一条不能破的约束：

   ```dart
   // 顺序不能改：AsyncData* 同时实现了 AsyncLoading，放在前面会被 loading 吞掉
   ```

2. **类 / 文件头：职责 + 指路** —— 一两行讲清它是什么，细节给 spec 路径：

   ```dart
   /// 示例缓存的读写（只碰行类 `DbArticle`，行↔模型转换在 `SampleService`）。
   ///
   /// 为什么在 feature 而不是 core，见 backend/database-guidelines.md「分工」。
   ```

3. **示例可以留** —— 调用方要照着写的形状（JSON 形状、一行用法）留在代码里，其余删掉。

---

## 哪些内容不放代码里

- 设计取舍与历史教训（「为什么不用 X」「曾经踩过 Y」）、规则的完整推导与验证命令 / 测试清单、成表格的对照（状态码映射、失败策略矩阵）

判断口径：**读代码的人要照着写 → 留代码；想弄明白为什么 → 放 spec。**

---

## 上限：一个注释块不超过 10 行

**超过 10 行的解释搬进 spec，代码里只留一行链接。**

- 按**连续注释行**计数，`//` 与 `///` 同等对待；空行或代码行把两块切开
- 门禁：**没有**。这条纯靠约定
- 限度只管 `lib/` —— `tool/` 脚本的头注释说明职责与用法，`test/` 的说明性注释同理

10 行是经验值，不是精确常数。需要更多空间时不要放宽阈值，把推导写进 spec。

---

## 引用 spec 的写法

指路统一写成 `<层>/<文件>.md「<章节>」`（示例见上文「代码注释」第 2 条）：

- **层目录不能省**（`backend/` / `frontend/`）—— 只写 `database-guidelines.md`，读者会以为是 `lib/` 下的文件。
- **不写 `.trellis/spec/` 前缀、不加反引号** —— 规范根是已知的，路径不是代码符号。
- **章节用标题里的关键词，不用 `§3.1` 这类编号** —— 编号会随文档改版漂移，关键词能直接 grep。
- **「见」和路径不许断行** —— 把 `见` 留在行尾、路径甩到下一行最难看。一行放不下就先把结论与指路拆成两段。
- 没有具体章节（整篇都相关，或章节还没写）就省略 `「章节」`，只留路径。

## spec 文档的语言
标题与正文都用中文，只有代码与标识符保持原文：

- **中文**：文档标题（`# 数据库规范`）、全部章节名与正文
- **保持原文**：代码、标识符（`AsyncView`、`ref.watch`）、路径与文件名、包名、命令与参数、技术专名（Drift、Dio、Retrofit、Mock、lint）
- **表头与英文标签也写中文**（`Purpose` / `When to use` / `**Rules**`）；代码块里当标签用的 `// BAD` / `// GOOD` 写成 `// 反例` / `// 正例`

## 快照式内容要单独标注

写死「当前代码状态」的句子必须带标注：

```markdown
> 快照（2026-09）：改动相关代码时请同步本节。
```

属于快照的内容：数量断言（「import `SampleItem` 的 9 个文件」）、枚举式清单（「现有 mock 规则：`GET /sample-items`、`GET /sample-items/{id}`…」）、盘点式结论（「目前全项目只有两处 `computed`」）。

更好的写法是**教怎么查**而不是给答案（如 `grep -rn "computed(" lib/`）。确实要给答案的，按上面的格式标注。

---

## spec 该怎么写

每个 guideline 文件都按这四条写：

1. 写**实际约定**，不写理想
2. 从**本仓库**取代码示例（能粘进编辑器就说明是准的）
3. 列出**禁止模式**
4. 快照式内容按「快照式内容要单独标注」处理

**只写结果与现状**：不写原因与推导（「因为…所以」「为了…才」）、不写后果与现象描述、不写历史与被否决的方案、不写日期叙事与 commit 号。跨层约定写进 `cross-cutting.md`；需要禁止的行为直接写成「不要做 X」。

属于**判据**的部分必须留 —— 拦截范围、全等比较、穷尽 `switch` 这类判定条件，读者要靠它判断某写法算不算违规。

另外两条值得考虑，但不是必须：**说明约束的真实强度**（有 lint / 脚本挡着的，与只靠 review 自觉的分开写，例：「`avoid_print` 未启用，这条是 review 约定」）；**明说「不存在什么」**（「没有 `domain/` 层」「没有 per-Notifier 日志」这类反向断言）。
