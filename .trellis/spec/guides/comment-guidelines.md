# 注释规范

> 代码注释只留「一句提示 / 这个类是做什么的 / 一个示例」；为什么这么设计、踩过的坑、完整规则放 `.trellis/spec/`。
>
> 本文件同时管四件事：**代码注释写什么**、**spec 引用怎么写**、**spec 自身的语言与快照约定**、**spec 该怎么写**。

---

## 代码注释：三条

1. **一句提示** —— 说明这段代码在做什么，或一条不能破的约束：

   ```dart
   // 顺序不能改：AsyncData* 同时实现了 AsyncLoading，放在前面会被 loading 吞掉
   ```

2. **类 / 文件头：职责 + 指路** —— 一两行讲清它是什么，细节给 spec 路径：

   ```dart
   /// 文章缓存的读写（只碰行类 `DbArticle`，行↔模型转换在 `ArticleService`）。
   ///
   /// 为什么在 feature 而不是 core，见 data/database-guidelines.md「分工」。
   ```

3. **示例可以留** —— 调用方要照着写的形状（JSON 形状、一行用法）留在代码里，其余删掉。

---

## 哪些内容不放代码里

- 设计取舍与历史教训（「为什么不用 X」「曾经踩过 Y」）
- 规则的完整推导、验证命令、测试清单
- 成表格的对照（状态码映射、失败策略矩阵）

判断口径：**读代码的人要照着写 → 留代码；想弄明白为什么 → 放 spec。**

---

## 上限：一个注释块不超过 10 行

**超过 10 行的解释搬进 spec，代码里只留一行链接。**

- 按**连续注释行**计数，`//` 与 `///` 同等对待；空行或代码行把两块切开
- 门禁：`comment_block_too_long` 规则（见 [cross-cutting.md](../cross-cutting.md)「架构边界与代码形态」），正反例在 `packages/app_lints/test/rules_test.dart`
- 限度只管 `lib/` —— `tool/` 脚本的头注释本身就是门禁的设计说明，`test/` 的说明性注释同理

10 行是「还能一眼看完」的经验值，不是精确常数。需要更多空间时不要放宽阈值，把推导写进 spec：那本来就是它该在的地方。

---

## 引用 spec 的写法

指路统一写成 `<层>/<文件>.md「<章节>」`：

```dart
/// 为什么在 feature 而不是 core，见 data/database-guidelines.md「分工」。
```

- **层目录不能省**（`data/` / `ui/`）。只写 `database-guidelines.md`，读者会以为是 `lib/` 下的文件。
- 根级文件（`directory-structure.md` / `type-safety.md` / `cross-cutting.md`）没有层目录，直接写文件名。
- **不写 `.trellis/spec/` 前缀** —— 规范根是已知的，前缀只会把注释行撑长。
- **不加反引号** —— 路径不是代码符号。
- **章节用标题里的关键词，不用 `§3.1` 这类编号** —— 编号会随文档改版漂移，关键词能直接 grep。
- **「见」和路径不许断行** —— 把 `见` 留在行尾、路径甩到下一行最难看。一行放不下就先把结论与指路拆成两段。
- 没有具体章节（整篇都相关，或章节还没写）就省略 `「章节」`，只留路径。

## spec 文档的语言

标题与章节名用中文，正文用中文：

- **中文**：文档标题（`# 数据库规范`）与全部 `##` / `###` 章节名；要保留的术语写成「中文（术语）」的形式（`# 本地化（l10n）`）
- **保持原文**：代码、标识符、路径、文件名、包名、命令，以及 Drift / Dio / Provider / ViewModel / Code Review / l10n / lint / Mock / HTTP 这类术语
- **不动**：表格表头与代码块内的标签（`// BAD` / `// GOOD`）—— 它们不参与「路径「章节」」引用，改它们只增加改动量、不提升可读性
- **特例**：`data/*.md` 的部分正文仍是英文段落（key 命名规则、读软写硬、drift `part` 约束、`@DriftAccessor` 报错文本），这是有意保留的信息，别为了「统一成中文」翻一遍

改章节名时同步改引用（见上一节）—— 引用写的是标题关键词，标题一改它就断了。
这道检查没有门禁，改完标题手工搜一遍引用（`git grep` 关键词）。

## 快照式内容要单独标注

写死了「当前代码状态」的句子必须带标注，否则会被当成永久事实 —— 而它会静默过期：

```markdown
> 快照（2026-09）：改动相关代码时请同步本节。
```

属于快照的内容：

- 数量断言（「import `Article` 的 9 个文件」）
- 枚举式清单（「现有 mock 规则：`GET /articles`、`POST /login`…」）
- 盘点式结论（「目前全项目只有两处 `computed`」）

更好的写法是**教怎么查**而不是给答案 —— 例如用 `grep -rn "computed(" lib/` 代替「全项目有两处 `computed`」。确实要给答案的那部分，按上面的格式标注。

## spec 该怎么写

每个 guideline 文件都按这四条写：

1. 写**实际约定**，不写理想
2. 从**本仓库**取代码示例（能粘进编辑器就说明是准的）
3. 列出**禁止模式**，并说明为什么
4. 记下**已经踩过的坑**（原始报错文本、当时的现象）

另外几条值得考虑，但不是必须：

- **说明约束的真实强度** —— 有 lint / 脚本挡着的，和只靠 review 自觉的，值得区分开（例：「`avoid_print` 未启用，这条是 review 约定」）
- **明说「不存在什么」** ——「没有 `domain/` 层」「没有 per-ViewModel 日志」这类反向断言，比正面描述更能挡住幻觉
- **提到门禁时只写「见 `justfile` 的 `verify`」，不写数量与项名。** 枚举一定会过期：门禁清单曾被逐项抄在
  8 处，加一道就要全改一遍；spec 里写死的 `tool/` 脚本数也已对不上。指针不会过期，枚举会。

---

## 为什么

spec 与注释是两份东西：spec 是「读一次就够、会随规则一起改」的长文，注释是「就地在眼前」的一句话。
把长文抄进代码，两处都要维护，改了一处另一处就成了假信息；而长注释会把实现淹掉，读者反而跳过它。
