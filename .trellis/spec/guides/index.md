# 思考指南

> 为什么会有这份：多数 bug 与技术债来自「没想到」，而不是「不会写」—— 没想到层边界会发生
> 什么、没想到同一个模式会重复、没想到边界情况、没想到后来的读者会直接跳过注释。
> 这份指南让你**在动手前先问对问题**。

---

## 速查：什么时候该触发思考

### 该想跨层问题时

- [ ] 功能跨 3+ 层（Page / ViewModel / Service / DAO）
- [ ] 数据在两个层之间换了类型（`DioException` → `Failure`、模型 → drift 行类）
- [ ] 同一份数据既走网络又走缓存
- [ ] 不确定某段逻辑该放哪一层
- [ ] 要在 `core/` 和 feature 之间挪东西（先看依赖方向）

→ 读 [跨层思考指南](./cross-layer-thinking-guide.md)

### 该想代码复用时

- [ ] 写的东西与已有代码相似
- [ ] 同一个模式重复出现 3 次以上
- [ ] 要给多个地方加同一个字段
- [ ] **正在改任何常量或配置**
- [ ] **正在新建工具 / 辅助函数** ← 先搜有没有现成的
- [ ] 同一个转换（如 `DioException` → `Failure`）被写到第 2 处

→ 读 [复用思考指南](./code-reuse-thinking-guide.md)

### 核查 AI 交叉复核结论时

- [ ] 复核者称「用户输入可能是恶意的」→ 先看真实数据源（内置清单？用户配置？外部 API？）
- [ ] 复核者指出「缺少校验」→ 这份数据来自可信的内部来源吗？
- [ ] 复核者称「行为变了」→ 读代码注释：这是不是有意的设计？
- [ ] 复核者在测试里找到「bug」→ 心里删掉被测功能，测试还过吗？还过 → 同义反复的测试

**AI 复核的常见误报模式**：

1. **可信边界误判**：把内部数据（打包进产物的 JSON 清单）当成不可信的外部输入
2. **无视设计注释**：把代码注释里写明的有意行为当成 bug
3. **变量看错**：没把变量追到真正的定义（例如 Map 的 key 是路径还是名字）

**确认规则**：每条 CRITICAL / WARNING 结论都要对着真实代码核一遍再谈优先级 —— 给 AI 复核留约 35% 的误报预算。

## 改任何值之前先搜（硬性）

> **改任何值之前，一律先搜。**

```bash
# 搜你要改的那个值
grep -r "value_to_change" .
```

> **用 `git grep`，别只用 Grep / ripgrep** —— 它们默认**跳过点号目录**（`.trellis/` `.cursor/`
> `.github/` `.agents/`），「全仓库扫描」会漏掉 spec、规则与 CI 配置；`git grep` 按 git 索引走。

这个习惯能挡掉绝大多数「忘了改 X」这类 bug。

## 怎么用这个目录

1. **动手前**：先扫一眼相关的那份思考指南
2. **写的过程中**：觉得重复或复杂，回来查
3. **踩坑之后**：把新洞见补进对应的指南
