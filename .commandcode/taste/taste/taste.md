# Taste
- Communicates in Chinese and expects replies and explanations in Chinese, even when the code/tooling is English. Confidence: 0.9
- Appreciates a concise end-of-work summary that separates real fixes from cleanups and explicitly flags anything left undone or unresolved. Confidence: 0.6
- Wants a complete, explicitly enumerated accounting of what remains unfixed after a round of work (not only what was changed), and will repeatedly follow up asking for the full remaining list. Treats that list as a work queue: starts the next batch by pasting one or more named items back almost verbatim (often with no added instruction at all — the quote itself is the approval) and expects exactly those items resolved end-to-end in one pass, leaving clearly separate items for later batches. Alternatively approves the whole enumerated list at once with a bare ordering instruction ("依次优化") and expects the items worked through in that order without re-asking. Confidence: 0.7
- Wants changes actually implemented (not just proposed) when approved, and verified before being declared done — run static analysis and the test suite (`flutter analyze` + `flutter test`) and report the results. Confidence: 0.7
- Gives a terse green light ("可以") or bare continuation ("继续") and expects the whole approved batch to be executed autonomously to completion — including test updates, doc/spec sync and fixing closely related blockers discovered mid-task — without stopping to re-ask for each one. Confidence: 0.6
- Prefers work staged into separate batches by risk — user-facing/runtime bug fixes first, structural refactors (routing, layering) as a distinct follow-up batch. Confidence: 0.45
- Relies on pre-commit hooks and CI (analyze/test jobs), so newly introduced lint warnings or failing tests are treated as blockers to fix. Confidence: 0.6
- Keeps project spec/docs (`AGENTS.md`, `.trellis/spec/*`) authoritative and up to date with the actual code; prefers fixing documentation drift rather than leaving stale specs. Confidence: 0.6
- Writes Dart doc/inline comments in Chinese and expects matching Chinese comments in generated edits. Confidence: 0.7
- Prefers removing dead code and duplicate logic over leaving it in place. Confidence: 0.6
- In the template/scaffold context, when a self-contained component (e.g. `FileStorage`, `AppDatabase.seed()`) has no consumer, prefers to keep it and give it a real consumer via a runnable example/demo page wired into the UI, rather than deleting it or inventing an artificial use — on the premise that template users who don't need it can delete it themselves. Expects the example to be clearly marked as deletable ("纯示例，可整目录删除"). Confidence: 0.65
- Values internal consistency: comparable components should follow one shared pattern (e.g. all models using the same freezed/serialization style), and inconsistency between them is treated as a defect worth fixing. Confidence: 0.5
- Prefers stable release dependency versions over pre-release/dev versions. Confidence: 0.5
- Favors reproducible, self-contained fixes: a fresh clone and CI should work with no manual out-of-band steps (no hand-downloaded/gitignored native libraries, no bespoke environment setup) — prefers solving via configuration that the toolchain regenerates over requiring developers to supply files by hand. Confidence: 0.55
- Treats removing a dependency as a change requiring explicit user sign-off rather than an autonomous cleanup; flags it for approval instead. Confidence: 0.5
- Chooses structural fixes that eliminate a root-cause architectural violation over annotating or tolerating it (e.g. moving shared types so the layer dependency direction is restored rather than documenting the wrong direction). Confidence: 0.4
- Regularly asks for a critical audit of the codebase's weaknesses ("这个项目还有什么缺点") or remaining optimization opportunities ("还能有什么优化？"), and expects concrete file/line evidence with severity, root-cause analysis and a prioritized fix order (by payoff/risk) rather than generic advice; also expects a clear recommendation of which items to tackle first. Confidence: 0.55
- Treats this project as a reusable template/scaffold, so app-release-specific concerns (signing keystore, minify/obfuscation, environment/production URL config) are intentionally out of scope and can be deferred to whoever builds a real app from it ("不着急…如果有真实开发 自己再去搞也可以") — does not want such deferred items repeatedly resurfaced as unfinished work, and approves documenting them explicitly as deliberate out-of-scope ("有意留白") in README/spec so future readers don't mistake them for TODOs. Confidence: 0.6
- Persisted preferences are validated defensively on load — a value outside the supported set (e.g. out-of-range theme index) falls back to a sensible default instead of crashing or misbehaving, and that fallback path is expected to be covered by tests. Confidence: 0.5
- Wants domain error types to carry a machine-readable code (enum) rather than a user-visible message string, with translation performed in the presentation layer; a `Failure` that bakes in a fixed-language message is treated as the root cause of untranslated errors, not a cosmetic gap, and fixing it (even though it touches the payload semantics of `AsyncState.error` and every error surface) is worth doing. Confidence: 0.55
- Wants raw technical error detail (server `statusMessage`, exception `message`/stack traces) to be structurally unable to reach the UI — logged only — instead of relying on developers remembering not to render it. Confidence: 0.5
- Prefers completeness enforced by the type system over convention: adding a new enum case should break compilation until the mapping and its localized strings are filled in, rather than counting on discipline to remember. Confidence: 0.45
- Prefers tests that exercise real implementations and real wiring (actual filesystem, real preferences/storage/DI because those layers already have their own tests) with mocks only at external boundaries such as network or repositories — over-mocking lower layers is seen as duplicative and as hiding wiring errors. Confidence: 0.55
- Treats newly added or changed user-facing code as needing test coverage, including tests that drive a page into its error/failure state, not just happy paths — a bug that only surfaces once a real test exercises that path is treated as a genuine defect to fix in the same batch. Confidence: 0.5
- Probes loose labels before acting on them: when told code is "dead/unused", asks for the distinction to be made precise (e.g. "是没用的还是没用上") and expects a per-item classification (redundant duplicate entry point vs. valid-but-unadopted API vs. actively wrong/harmful) with evidence, rather than one lumped "delete it" verdict. Confidence: 0.45
- Before green-lighting a suggested next step, probes it before committing: either its difficulty/feasibility ("好做吗？") or, when the step builds on existing infrastructure, whether that infrastructure is even necessary/worth it ("先看 X 有没有必要"). Confidence: 0.4
- Uses `git worktree` to keep multiple branches checked out side by side in separate directories (e.g. a dedicated `master` worktree alongside the feature-branch checkout) rather than switching branches in place, and refers to branches by worktree location. Can give commands referencing absolute local paths outside the current workspace. Confidence: 0.5
- Tolerant of irreversible/destructive operations: when offered "back up first, then overwrite" versus "overwrite directly, no backup", picks the direct no-backup path and accepts losing uncommitted work — favors getting the task done over precautionary safety steps. Same instinct on environment cleanup: warned that deleting program data (session history, login state) is unrecoverable, still chooses the full-removal option over one that preserves data for a possible reinstall. Confidence: 0.5
- Not every question is about the current repo: when asking about a tool or technology (e.g. "pi agent 还能有什么优化？") may mean the upstream product/library itself, not this project's local integration/usage of it — expects the scope disambiguated rather than defaulting to the current codebase ("抛开本项目的"), and expects the general/upstream answer grounded in real evidence (e.g. reading the installed package source/docs) rather than speculation. Confidence: 0.4
- Asks open-ended comparative evaluation questions about the project ("这个项目怎么样 和兄弟分支比") with almost no context and expects the agent to first establish the facts (branch layout, what alternatives actually exist, real diff size) before judging, then deliver an evidence-backed verdict on which version is the better base — naming what is genuinely better, what was traded away, and any latent breakage on the losing side — rather than a neutral description of both. Extends this to keep-or-kill value questions about artifacts that already exist — e.g. asking whether a set of parallel preset branches deserves to exist at all ("那些分支有存在的价值吗？") — expecting a principled verdict on how many variants should exist and why the rest shouldn't, backed by concrete cost evidence (per-variant sync/maintenance burden), rather than assuming anything already built is justified.
